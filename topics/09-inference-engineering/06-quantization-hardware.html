Quantisation and choosing GPUs

Two problems that are really one: how many bytes each weight takes, and how fast a GPU can move those bytes. Pick a number format, prove it didn't break the model, then pick the hardware with arithmetic instead of brand loyalty.

Start here (no maths needed)

A model is billions of numbers. Writing each number with fewer digits makes the model smaller and faster, as long as you check it still gives good answers. Then you pick the computer whose memory is big enough and fast enough for the job.

Think of it like this

Imagine moving house with a delivery van. Your stuff is the model. You can pack each item in a big padded box (16-bit numbers), a smaller box (8-bit) or squash it into a tiny pouch (4-bit). Smaller packing means fewer trips and a smaller van, but squash a lamp too hard and it breaks. Clever packers put a label on every small bundle saying how big the things inside really are, so they unpack correctly. Choosing the van is the second question: a bigger van holds more, a faster van finishes sooner, and a cheap van might be fine if your stuff is small.

How it works

  1. Each weight is normally stored as a 16-bit number. Quantisation stores it in 8 or 4 bits instead.
  2. A "scale" number stored next to a group of weights says how to stretch the small numbers back to their real size.
  3. Smaller groups, each with its own scale, make fewer mistakes but cost a little extra memory.
  4. You test the squashed model against the original on the same questions, and accept it only if the drop is smaller than the normal noise.
  5. Then you check which GPU can hold the model plus its notes (the KV cache) and read it fast enough.

Why robots care

A robot's computer has a small memory and a slow memory bus compared with a data-centre GPU. A model that answers in 10 ms in the cloud can take ten times longer on the robot. Quantising to 4 or 8 bits is often the difference between a model that fits on board and reacts in time, and one that doesn't.

Try it

  • Write the numbers 0.12, 0.5, 0.71 and 9.6 using only whole numbers from −7 to 7, after choosing one "multiply by" label for all four. Then try again with a separate label for the small three and for 9.6. Which version keeps the small numbers?

Problem 11 · FP8 vs INT8 vs INT4 vs NVFP4: pick one and measure the loss

What the interviewer is testing: whether you know what each format actually stores, why outliers decide what works, which hardware runs which format natively, and whether you can design an evaluation that tells a real quality drop from noise.

The concepts

Integer formats. Map a real value x to an integer with a scale s, and back:

symmetric INT-b:   q = clamp(round(x / s), −(2^(b−1) − 1), 2^(b−1) − 1)
                   x̂ = s × q,     s = max|x| / (2^(b−1) − 1)
INT8: q ∈ [−127, 127]      INT4: q ∈ [−7, 7]

granularity of s:  per tensor  →  per channel (row)  →  per group (e.g. 128 values)

Integer steps are evenly spaced, so one large value forces a large scale and crushes the small ones. Example: a group holding 0.05, 0.3, −0.2 and one outlier of 20, in INT8 per tensor. s = 20/127 = 0.157, so 0.05 rounds to 0 and 0.3 becomes 0.31. Activations in large LLMs have exactly this pattern: a few channels with values far larger than the rest. LLM.int8() (Dettmers et al., 2022) keeps those channels in 16 bits. SmoothQuant (Xiao et al., 2023) moves the difficulty from activations into weights with a per-channel rescaling, so both can use INT8.

Floating-point formats. FP8 comes in two variants (Micikevicius et al., 2022): E4M3 (4 exponent bits, 3 mantissa bits, max ±448), used for weights and activations in inference, and E5M2 (more range, max ±57,344), mostly for gradients. Floating-point steps are fine near zero and coarse for big values, which suits bell-shaped weight distributions and tolerates outliers better than INT8 at the same bit count.

INT4 weight-only. GPTQ (Frantar et al., 2022) quantises weights one column at a time and uses second-order information to compensate for the error in the remaining columns. AWQ (Lin et al., 2023) protects the small share of weight channels that see large activations by scaling them before rounding. Both usually use groups of 128 with a 16-bit scale, so the real cost is 4 + 16/128 = 4.125 bits per weight. Activations stay in 16 bits, so the matrix multiply still runs at 16-bit speed. The gain is in bytes moved, which is what limits decode.

NVFP4. According to NVIDIA's Blackwell documentation, NVFP4 stores each value as E2M1 (1 sign, 2 exponent, 1 mantissa bit, so values from about −6 to 6). Every block of 16 values shares an FP8 E4M3 scale, and each tensor also has one FP32 scale. That's about 4.5 bits per value. NVIDIA describes it as roughly 3.5× smaller than FP16 and 1.8× smaller than FP8. MXFP4, the OCP format, uses 32-value blocks with a power-of-two scale. NVFP4's smaller blocks and fractional scales are meant to cut the rounding error. Blackwell tensor cores run it natively.

NVFP4:   x̂ = s_tensor (FP32) × s_block (E4M3, one per 16 values) × q (E2M1)
bits per value ≈ 4 + 8/16 = 4.5   (plus one FP32 per tensor)

Worked answer with real numbers

Assumptions: a Llama-3-70B-shaped model (nominal 70B parameters, 80 layers, 8 KV heads, head dim 128), batch 1, decode bandwidth floor = weight bytes ÷ HBM bandwidth (ignores KV and overhead). Bandwidths from NVIDIA's spec tables: H100 SXM 3.35 TB/s, H200 SXM 4.8 TB/s.

NVFP4      70e9 × 4.5/8 =  39 GB   any of them             (no native FP4)        (no native FP4)

* 140 GB on a 141 GB H200 leaves almost nothing for the KV cache: not deployable.

Going from BF16 to FP8 halves the bytes and therefore roughly halves the decode floor. It also frees memory for a bigger batch, so throughput gains are often larger than 2×. Going to 4 bits halves the bytes again.

My pick, and the measurement plan. On H100 or H200, pick FP8 W8A8 (per-channel weight scales, dynamic per-token activation scales), with FP8 KV cache as a separate, later step. It is natively supported, well supported in vLLM, SGLang and TensorRT-LLM, and usually close to lossless. On B200, evaluate NVFP4 for weights, because it buys another ~1.8× in memory over FP8. Measure the loss like this:

  1. Freeze the baseline: same engine, same prompts, greedy decoding (temperature 0) for deterministic tasks.
  2. Cheap signal first: perplexity on held-out text, and the KL divergence between baseline and quantised next-token distributions. These catch broken quantisation fast, but small perplexity changes don't map cleanly to task quality.
  3. Task evals: knowledge (MMLU-style), maths (GSM8K-style), code, long-context retrieval, and your own production eval set. Quantisation damage often shows up first in maths, code and long contexts.
  4. Know the noise: standard error of an accuracy is √(p(1−p)/n). MMLU has 14,042 test questions: at 70% accuracy the SE is 0.39 points, so a 95% interval is about ±0.8 points. GSM8K has 1,319: at 80% the SE is 1.1 points, about ±2.2. A 1-point drop on GSM8K is inside the noise. Use paired comparisons on the same questions, or a bootstrap, before you claim a difference.
  5. Set the gate in advance, for example "no task drops more than 1 point absolute beyond noise, and the production eval's win rate against baseline is at least 48%". Then measure the payoff: tokens/s, ITL at p99, max batch, memory.

How to say it in the interview

Decode is bandwidth-bound, so bits per weight translate almost directly into tokens per second and into how many users fit. On Hopper I'd pick FP8 W8A8 with per-channel weight and per-token activation scales: it's native, about 2× fewer bytes and usually near-lossless. INT4 weight-only and NVFP4 roughly halve the bytes again, and NVFP4 runs natively on Blackwell, but the risk is higher, so they need stronger evidence. I'd measure the loss with perplexity and KL as smoke tests, then paired task evals including maths, code, long-context and our own traffic, with confidence intervals so I don't mistake noise for loss. I'd set the acceptance gate before looking at results, then report the speed and memory gains alongside.

Common mistakes

  • Calling INT4 weight-only "4× faster". It moves fewer bytes, but the math still runs in 16-bit, and at large batch dequantisation can become the bottleneck.
  • Judging quality by perplexity alone. Perplexity can barely move while maths or long-context retrieval drops.
  • Ignoring eval noise. A 1-point change on a 1,319-question benchmark is not evidence.
  • Forgetting that the KV cache and activations are separate decisions from weight precision.

Problem 12 · Pick GPUs for a workload: H100 vs H200 vs B200 vs L40S

What the interviewer is testing: whether you start from the workload (model size, precision, context, latency target, traffic) and turn specs into memory fit, max batch, latency floor and cost per token, rather than quoting peak FLOPS.

Worked answer with real numbers

Workload: a 70B-shaped model in FP8 (70 GB of weights), FP8 KV cache, 4,096 tokens of context per sequence, batch 64. KV per sequence = 2 × 80 × 8 × 128 × 4,096 × 1 B = 671 MB. Assumptions: 90% of HBM is usable (the rest goes to activations and the runtime), the bandwidth floor is reached exactly, and tensor-parallel communication is free. All three flatter the GPUs, the last one especially for PCIe cards. Hourly prices are assumptions for illustration only (H100 $2.50, H200 $3.50, B200 $6.00, L40S $1.20 per GPU-hour). Real prices vary widely by provider, contract and month.

What this shows:

  • Memory decides the count before speed does. One H100 can't hold a 70B FP8 model plus a useful cache. One H200 can, which is its main selling point: it has the same compute as the H100, with 1.76× the memory and 1.43× the bandwidth.
  • Cost per token tracks $/h ÷ bandwidth for decode. At the assumed prices, H100, H200 and B200 land within a few percent of each other, because their price per TB/s is similar (0.75, 0.73, 0.75). The ranking flips with small price changes, so use your own quotes.
  • B200's extra lever is FP4. NVFP4 cuts the weight bytes from 70 to 39 GB, so the same GPU is about 27% cheaper per token in this model, if the quality gate passes.
  • L40S loses on big models. 864 GB/s per card, no NVLink, and tensor parallelism over PCIe Gen4 make 70B expensive and slow. Its case is small models, PCIe-only data centres, lower power and price, and mixed vision or graphics workloads. A rule of thumb: for decode it only matches an H100 per token if it costs less than 1/3.9 of the H100's price, since 3.35 / 0.864 ≈ 3.9.

Second workload, to show the other side: an 8B model in FP8 with 2K context. One L40S fits it with room for 262 sequences. At batch 64 the floor is 19.2 ms per token and 3,333 tokens/s, about $0.10 per M tokens at the assumed $1.20/h. That's acceptable for a 50 ms ITL target, and it runs in ordinary PCIe servers. An H100 is faster (5.0 ms, about $0.05 per M at the assumed price), so the L40S wins only if H100s are scarce, the price gap is wider, or power and rack limits rule.

How to say it in the interview

I start from the workload: model size and precision, context length, traffic shape, and a latency target such as 50 ms ITL at p99. From that I compute whether weights plus cache fit, the max batch, the decode floor of bytes per step over bandwidth, and the prefill time from dense FLOPS. Then I turn throughput into cost per million tokens with real price quotes. For a 70B FP8 model, one H200 replaces two H100s because of its 141 GB, B200 wins on throughput and on FP4 if quality holds, and L40S suits small models in PCIe servers. Finally I'd benchmark the top two candidates on our actual traffic, because the floor ignores communication, kernels and scheduling.

Common mistakes

  • Comparing sparse TFLOPS. NVIDIA's headline rates assume 2:4 sparsity; dense LLM inference gets half.
  • Mixing SXM and PCIe numbers. H100 SXM and H100 NVL differ in memory, bandwidth, power and interconnect.
  • Ranking by FLOPS for a decode-heavy service. Bandwidth and memory capacity usually decide it.
  • Presenting prices as facts. They change monthly; show the formula and plug in quotes.

Practise it

(a) Fake-quantise a small model and measure the loss (laptop or free Colab). Round-trip the weights of every linear layer through INT8 or INT4 with different group sizes, then compare perplexity. This needs no special hardware, because the maths runs in 16 or 32 bits.

import torch, math
from transformers import AutoModelForCausalLM, AutoTokenizer
from datasets import load_dataset

def fake_quant(w, bits=4, group=128):
    qmax = 2 ** (bits - 1) - 1
    g = w.reshape(-1, group)
    s = g.abs().amax(1, keepdim=True).clamp(min=1e-8) / qmax
    return (torch.clamp(torch.round(g / s), -qmax, qmax) * s).reshape(w.shape)

def ppl(model, tok, text, n=256, steps=40):
    ids = tok(text, return_tensors="pt").input_ids[:, : n * steps]
    nll = 0.0
    with torch.no_grad():
        for i in range(steps):
            x = ids[:, i * n : (i + 1) * n]
            nll += model(x, labels=x).loss.item()
    return math.exp(nll / steps)

name = "Qwen/Qwen2.5-0.5B"
tok = AutoTokenizer.from_pretrained(name)
text = "\n\n".join(load_dataset("wikitext", "wikitext-2-raw-v1", split="test")["text"])
for bits, group in [(16, 0), (8, 128), (4, 128), (4, 32)]:
    m = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float32).eval()
    if bits < 16:
        for mod in m.modules():
            if isinstance(mod, torch.nn.Linear) and mod.weight.numel() % group == 0:
                mod.weight.data = fake_quant(mod.weight.data, bits, group)
    print(bits, group, round(ppl(m, tok, text), 3))
  • Measure: perplexity for each setting, plus bits per weight including scales (4 + 16/group). Expect INT8 to be nearly free and INT4 at group 32 to beat group 128.
  • Add an outlier: multiply one input channel of a layer by 50 before quantising, and watch per-tensor INT8 break while per-group survives.
  • Then run a small task eval (for example lm-evaluation-harness on a GSM8K subset) on the 16-bit and INT4 versions, and compute the standard error before deciding whether they differ.

(b) The real thing (one Hopper or newer GPU). Make an FP8 checkpoint of an 8B model with TensorRT Model Optimizer or vLLM's quantisation tooling, serve both versions in vLLM, and compare tokens/s, ITL at p99 and the KV-cache capacity vLLM reports at startup. Then run the same evals on both. (c) Re-create the worked GPU table in a spreadsheet with your own price quotes and an ITL target, and see which GPU wins.

Why it matters for robotics

  • Robot memory is small and slow. NVIDIA lists the Jetson AGX Orin 64GB module at 64 GB of LPDDR5 and 204.8 GB/s, and the Orin NX 16GB at 102.4 GB/s. That's about 1/16 and 1/33 of an H100 SXM's bandwidth. An 8B model in INT4 (≈4 GB) has a decode floor of about 20 ms on the AGX module and 40 ms on the NX. In BF16 it would be 78 ms and 156 ms.
  • Memory is shared. On these modules the CPU, perception and the model share one pool, so the model's footprint competes with camera buffers and maps. Quantisation is often what makes the model fit at all.
  • Check the format against the chip. FP8 and NVFP4 results come from data-centre GPUs. Check which formats your module's tensor cores and inference stack support before you plan on them; INT8 and INT4 weight-only are the common edge choices.
  • Evaluate on robot tasks. A quantised VLA can match on language benchmarks and still lose precision on fine actions. Gate on task success in sim and on hardware, not only on perplexity.
  • GPU selection for a fleet backend is the cloud version of this page. The H100/H200/B200/L40S choice applies to servers that train or serve many robots, not to the robot itself.

Self-check

How many bits per weight does INT4 with group size 64 and an FP16 scale really cost?

4 + 16/64 = 4.25 bits per weight.

Why does a single activation outlier hurt per-tensor INT8 more than FP8?

INT8 steps are evenly spaced, so the outlier sets a large scale and small values round to zero. FP8 has finer steps near zero and coarser steps for big values, so it keeps small values better at the same bit count.

A quantised model scores 79.0% on GSM8K (1,319 questions) against 80.0% for BF16. Is that a real loss?

Not on its own. The SE at 80% is about 1.1 points, so a 1-point gap is within noise. Use a paired comparison on the same questions or a bootstrap, and look at other tasks too.

Why is an H200 not faster than an H100 for a compute-bound prefill?

NVIDIA lists the same tensor-core rates for H100 SXM and H200 SXM. The H200 gains memory capacity (141 vs 80 GB) and bandwidth (4.8 vs 3.35 TB/s), which help decode and batch size, not raw FLOPS.

A 70B FP8 model with 671 MB of KV per sequence runs on one H200 with 90% usable memory. What's the max batch?

Usable = 0.9 × 141 = 126.9 GB. Minus 70 GB of weights = 56.9 GB. 56.9 / 0.671 ≈ 84 sequences.

NVIDIA's table says "FP8 3,958 TFLOPS" for H100 SXM. What number do you use for dense inference?

Half: 1,979 TFLOPS. The headline figure assumes 2:4 structured sparsity.
