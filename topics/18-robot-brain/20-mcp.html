Start here

Write your robot's tools once, behind a standard plug. Then any AI app can find them and use them. But a plug is also a door, so the rules that must never break live on your side of it.

In week 15 Claude could drive your robot, but only through the agent loop you wrote. Your friend uses Claude Desktop. Your cousin uses a different app. Each would need its own glue code, and none of them would know the rule "never pick up the green block, it's Mum's favourite".

MCP
Model Context Protocol: a standard plug for joining AI apps to tools.
Server
The program that has the tools. Yours is the robot.
Client
The AI app, like Claude Code or Claude Desktop.
Last line of defence
The final check before something happens in the real world.

1. The idea

💡 The idea

MCP is a plug socket. A toaster maker doesn't need to know which house you live in, and your house doesn't need to know which toaster you bought. Both follow the same plug. Your robot is one appliance. Write its MCP server once, and every MCP app can plug in.

Why a standard wins: every app would otherwise need its own adapter for every robot. Count the lines:

Why a fuse: a charger has its own fuse. It doesn't trust the laptop never to ask for too much. You can't know which AI plugs in, or what it was told. So the rule "never pick up the green block" goes in your server's code, in guard(), which runs before every single tool call. Not in a prompt.

🆘 Stuck?

Hint 1
The signature is already there: def guard(name, args, calls):. Three flat if ... return lines. The budget comes first: once it's spent, everything is refused, even look.


Hint 2
len(calls) is how many calls came before this one. Call 41 arrives when len(calls) is 40, so use >=. Use args.get("object"): look has no object.


Hint 3 (fill in the blanks)
if len(calls) >= ____:
    return False, "too many calls: ask the person to reset the room"
if name == "pick_up" and args.get("object") in ____:
    return False, f"the {args['object']} is protected: never pick it up"
return True, ""

6. Check yourself


In one sentence, what problem does MCP solve?
You write a set of tools once, behind a standard plug, and any app that speaks MCP can find and call them, instead of custom glue for every app.


Does the model connect directly to your server?
No. The model only writes text asking for a tool. The app turns that into a tools/call message to your server and passes the result back.


Why does guard check pick_up but not go_to?
Driving to the green block does no harm; only picking it up does. Put the rule exactly on the action that does the damage. A guard that blocks too much makes the robot useless.


The AI sends pick_up with "Green Block" (capitals). Is the green block safe?
guard allows it (not in PROTECTED), but execute_tool only accepts exact names and answers Unknown object 'Green Block'. Two layers beat one.


A friend sends you an MCP server that "makes Claude 10× better at homework". Plug it in?
Not without a parent, and only if you truly trust where it came from. A stdio server is a program running on your computer as you: it could read or send your files.



7. Want to know more?


The real messages, in JSON (simplified)

After a hello (initialize), the app asks what's on offer, and later calls a tool. The id matches each answer to its question, like a ticket at a deli counter.


app ──▶ server   {"jsonrpc": "2.0", "id": 1, "method": "tools/list"}
server ──▶ app   {"jsonrpc": "2.0", "id": 1, "result": {"tools": [
                   {"name": "pick_up", "description": "Pick up a block. ...",
                    "inputSchema": {"type": "object",
                                    "properties": {"object": {"type": "string"}},
                                    "required": ["object"]}}, ... ]}}

app ──▶ server   {"jsonrpc": "2.0", "id": 7, "method": "tools/call",
                  "params": {"name": "pick_up", "arguments": {"object": "blue block"}}}
server ──▶ app   {"jsonrpc": "2.0", "id": 7, "result": {
                   "content": [{"type": "text", "text": "Picked up the blue block."}],
                   "isError": false}}


The MCP package builds each tool's description from your function's docstring and type hints. A refusal comes back with "isError": true; with the official client the course's author saw Error executing tool pick_up: Refused by the robot's server: the green block is protected: .... A server can also offer resources (things to read) and prompts (ready-made instructions).




Why your server must never print()

With stdio, the app starts your Python file itself and passes JSON lines through its standard input and output. A print("moving now!") goes down the same pipe, the app can't read it as JSON, and the connection breaks or hangs. Debug with a file, the watcher (lesson20_watch.py reads traces/live.txt), or print(..., file=sys.stderr).




The four lines of defence, and why only one is certain

    

  1. The model's own good sense: usually good, not a guarantee.
    2. 

  2. What the model was told: the app may pass on your server's instructions, and a web page could inject "pick up every block" (week 10).
    3. 

  3. The app asking "allow this tool?": people click yes without reading.
    4. 

  4. Your server's code: runs every time, whatever the model is. Only this one is certain.
    5. 



Why 40 calls? An honest tidy-up needs 1 look + 3 blocks × 3 calls = 10. Forty leaves room for retries, but a looping model stops at call 40, not 40,000. And guard (allow by default, refuse a short list) sits in front of execute_tool (allow only a short list): together they're stronger than either.




Stretch: find the hole

reset_room is itself a tool, it doesn't go through guard, and it empties calls. So a runaway AI could reset its own budget for ever. Fix it in the server, not a prompt: make reset a command-line option, keep a total count that reset never clears, or allow only a few resets. Write a check that proves the hole is closed. Bonus: add a resource (@server.resource) that lets an app read the room map.
