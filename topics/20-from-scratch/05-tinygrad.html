tinygrad: a deep learning framework you can read

Something between micrograd and PyTorch. It waits until you need an answer, then glues your maths into as few GPU programs as it can.

Start here (no maths needed)

tinygrad doesn't do your sums straight away. It writes them down as a plan, then turns the whole plan into a few fast programs for the computer's chip.

Think of it like this

You need eggs, milk and bread. You could walk to the shop three times, once for each thing. Or you could write a shopping list and go once. tinygrad is the shopping-list person. Every time you ask it to multiply or add, it only adds a line to the list. When you finally say "I need the answer now", it looks at the whole list and does it in as few trips as possible. Each "trip" is a small program, called a kernel, that runs on the chip.

How it works

  1. You write normal-looking maths: multiply these, add those, take the biggest.
  2. tinygrad doesn't calculate yet. It builds a plan (a graph of steps).
  3. When you ask for a result, it squeezes neighbouring steps together. This is called fusing.
  4. It writes real code for your chip (C for the CPU, Metal for a Mac's graphics chip) and runs it.
  5. Learning works the same way: it plans the "which way should each number move?" sums too, then runs them.

Why robots care

A robot has a small computer and a battery. It can't waste trips. Fewer, bigger programs mean faster answers and less power. comma.ai's openpilot, a driver-assistance system that runs on a small computer in a car, uses tinygrad to run its driving model.

Try it

  • Write a shopping list for a meal. Now group it by shop aisle so you walk the shortest path. That's what fusing does to maths.
  • If you have a Mac or Linux laptop, follow the commands in Run it, tested. The tiny XOR example finishes in about 5 seconds.

Words to know

Tensor
A box of numbers: a list, a grid, or a stack of grids.
Lazy
Waits until the answer is really needed before doing the work.
Kernel
One small program that runs on the chip and does a chunk of the maths.
Fusing
Joining several steps into one kernel so the chip does one trip, not many.
Backend
The part that knows how to talk to one kind of chip: CPU, Mac GPU, NVIDIA GPU and so on.
Autograd
The computer works out the "which way to nudge each number" maths for you.

1. Summary

TL;DR

tinygrad is a complete deep learning stack (tensors, autograd, a compiler, optimisers, datasets) that its README places "between PyTorch and karpathy/micrograd". Its trick is laziness: operations build a graph, and only .realize() (or reading a value) turns that graph into kernels. Because it sees the whole graph first, it can fuse many operations into one kernel. On our Mac, a matmul written as "reshape, multiply, sum" became exactly 1 kernel on the Metal GPU. Forcing the multiply to happen first made 2 kernels and a 67 MB temporary array.

  • PyTorch-like API: Tensor, .backward(), nn.Linear, nn.optim.Adam. Most training loops look familiar.
  • The compiler is in the repo: the graph format (UOps), the scheduler, the code generators and the device runtimes are all plain Python you can open.
  • Many backends, few ops: the README says a new accelerator "only needs to support a total of ~25 low level ops".
  • Debug as a teaching tool: DEBUG=2 prints each kernel and its time. DEBUG=3 adds the optimisations chosen. DEBUG=4 prints the generated code.
  • Tested here: the README's gradient example, the fusion demo, a tiny XOR network and the full beautiful_mnist.py (97.97% and 98.24% test accuracy in two runs on an M4).
  • Robo-Helper test: our Lesson 15 brain, ported to tinygrad, gives identical answers. It writes the same plans on all 50 held-out examples. It is slower for one command (about 2–4.5 ms vs 0.5 ms) but wins from batches of 16, and is about 76–333× faster at 4,096 commands (section 4).
  • Used in a real product: openpilot includes tinygrad as a git submodule, and its model daemon imports it (checked in the openpilot repo, see section 5).

2. How the code works

There are four layers. Each is a folder in tinygrad/.

  1. Tensor front end (tensor.py, mixin/). Methods like reshape, * and sum don't touch numbers. Each one wraps a UOp: a node that says "this is a multiply of those two inputs". So c = a * b just grows a graph.
  2. Autograd (mixin/gradient.py). .backward() walks the graph backwards and adds more UOps for the gradients. Gradients are also lazy, so the backward pass gets fused too.
  3. Scheduler (schedule/). When you call .realize(), it decides where a result must be stored in memory, and cuts the graph into kernels at those points. Everything between two stored results becomes one kernel.
  4. Codegen and runtime (codegen/, renderer/, runtime/). Each kernel is optimised (loop splitting, tensor cores, vector loads), then a renderer writes source code: C for the CPU (ClangRenderer), Metal Shading Language for Apple GPUs (MetalRenderer), CUDA, and others. A runtime such as ops_metal.py (282 lines) compiles it and launches it.

The whole "lazy" idea fits in one method. Nothing runs until here:

# tinygrad/tensor.py (MIT, tinygrad authors), trimmed
def realize(self, *lst:Tensor, do_update_stats=True) -> Tensor:
  """Triggers the computation needed to create these Tensor(s)."""
  to_realize = [x for x in (self,)+lst if x.uop.base.needs_storage()]
  if len(to_realize):
    linear, var_vals = Tensor.linear_with_vars(*to_realize)
    run_linear(linear, var_vals, update_stats=do_update_stats)
  return self

linear_with_vars builds the list of kernels. run_linear compiles and runs them. Reading a value with .item(), .tolist() or .numpy() calls realize for you.

The one idea that makes it click

Look at the README's matmul: (a.reshape(N,1,N) * b.T.reshape(1,N,N)).sum(axis=2). Read literally, it builds an N×N×N cube of products, then sums it. For N = 1024 that cube would be about a billion floats, 4 GB. An eager library would build it. tinygrad sees "multiply, then sum" in the same graph, so it writes one kernel that multiplies and adds inside a loop, never storing the cube. Here is the actual C it generated on the CPU backend for N = 4 (DEBUG=4 DEV=CPU):

// generated by tinygrad for N = 4, trimmed
for (int Lidx1 = 0; Lidx1 < 4; Lidx1++) {
  float4 val3 = *((float4*)(((float*)(val1))+alu0));   // one row of a
  for (int Lidx2 = 0; Lidx2 < 4; Lidx2++) {
    ...
    *(((float*)(val0))+(alu0+Lidx2)) =
      ((val3[0]*val7)+(val3[1]*val5)+(val3[2]*val6)+(val3[3]*val4));
  }
}

Multiply and add, in one loop, writing only the 4×4 answer. That is kernel fusion. The reshapes cost nothing: they only change how indexes are computed.

3. Run it, tested

All commands were run on 7 Nov 2026 on a MacBook (Apple M4, 16 GB), Python 3.14.5, in a private venv in a scratch folder. Device.DEFAULT reported METAL, so the GPU runs below are on the Mac GPU. Clang warning lines have been trimmed from the outputs.

Install, and one fix that was needed

git clone --depth 1 https://github.com/tinygrad/tinygrad.git
python3 -m venv venv
./venv/bin/pip install -e tinygrad
./venv/bin/python -c "from tinygrad import Device; print(Device.DEFAULT)"
METAL

The first run failed. On current master, Metal kernels are submitted by a small helper program that tinygrad compiles for the CPU, and by default it uses LLVM. This Mac has no Homebrew LLVM, so every realize crashed:

loading llvm failed: not found on system
AttributeError: failed to load library llvm: try setting LLVM_PATH?

The fix was to tell tinygrad to build that helper with Apple's own clang instead (the setting is in tinygrad/helpers.py). Installing LLVM with Homebrew would also work, but this needs nothing new:

export HCQ_RUNTIME_DEV=CPU:CLANG

x = Tensor.eye(3).clone(); y = Tensor([[2.0,0,-2.0]])

Fused vs forced, counted

To see what laziness buys, this script runs the same maths twice at N = 256: once lazily, once forcing the big product to be stored first. GlobalCounters.kernel_count counts kernels.

# lazy.py (written for this page)
c = (a.reshape(N, 1, N) * b.T.reshape(1, N, N)).sum(axis=2)
c.realize()                                  # lazy: one plan, then run
p = (a.reshape(N, 1, N) * b.T.reshape(1, N, N)).realize()
d = p.sum(axis=2).realize()                  # forced: store p, then sum

4. Connect to Robo-Helper (Module 18)

Measured on 8 Nov 2026, with the first version of Robo-Helper's training data: 350 examples, which by accident included 3 of the 12 bake-off commands. On 9 Nov those were removed (343 examples). The small Module 18 brains' bake-off scores didn't change, and the tiny LM's held-out score went from 86% to 92%. Every brain here was compared on the same data, but if you re-run, expect the exact numbers to move by a few points.

Robo-Helper is standard-library Python: no numpy, no torch. That was on purpose, so you could see every number. tinygrad is the next rung up the ladder:

RungWhat computes gradientsWhat runs the maths
Lesson 4, neuron and Lesson 15, tiny LMYou, by hand (manual backprop, checked against numerical gradients)Python loops over lists
micrograd (page 1)Autograd over single numbersPython, one number at a time
tinygradAutograd over whole tensors, itself lazyGenerated kernels, fused, on CPU or GPU
PyTorchAutograd over tensorsHuge hand-written kernel libraries (optionally a compiler)
  • Lesson 16, How fast is a brain? taught you to measure latency, p50 and p95. tinygrad shows where the time goes inside one answer: DEBUG=2 prints every kernel and its microseconds. Our XOR run shows the lesson's point the other way round: 4 examples on a GPU took 5.2 s, because launching and compiling cost more than the maths.
  • Lesson 17, Faster and cheaper made the brain faster by caching, quantising (4-bit kept 100% accuracy, 2-bit dropped to 75%) and distilling. Kernel fusion is a fourth trick from the same family: same answer, less memory traffic. TinyJit is a cache too. It records the kernels of the first calls and replays them, so later calls skip planning.

What the numbers say, honestly:

  • Correct: the tinygrad brain writes exactly the same plan as the Lesson 15 brain on all 50 test_data() examples. Both get 86% of plans exactly right, so the port changes nothing about how good the brain is. The 4-bit copy from Lesson 17's quantized_copy also matches its pure-Python twin on 50/50. (Our tensors still hold the 4-bit values as 32-bit floats. The 1,351 bytes is what it would take packed, using Lesson 17's size_bytes. We didn't pack it. The course's "tinylm-4bit" brain is the distilled model, which has more weights, hence its 1,411 bytes.)
  • One command at a time, tinygrad is slower. Pure Python decides in about 0.4–0.5 ms. tinygrad with TinyJit takes about 2 ms on Metal and 4.5 ms on CPU. Without the JIT it takes 50–110 ms, because it plans and schedules the graph on every call. For this tiny model, the overhead is bigger than the maths.
  • Batches flip it. With the JIT, tinygrad wins from a batch of 16 on both backends. At 4,096 commands at once it is about 76× faster on CPU (2,173 ms vs 28.5 ms) and about 333× faster on Metal (1,980 ms vs 5.9 ms). Without the JIT it starts winning somewhere between 64 and 512.
  • The numbers are noisy. The laptop was running other jobs (load average 8–24 during these runs), which is why the no-JIT column jumps around (for example 110.8 ms at batch 16). On 7 Nov the older single-action model gave the same pattern: tinygrad lost on one command and won from a batch of 16. Treat these as rough sizes.

When does this matter on a robot? Robo-Helper hears one command every few seconds. A half-millisecond pure-Python brain is already fast enough, and the tinygrad version would make each decision slower. Batching pays off when a robot must score many things at once: every candidate route, every object in a camera frame, a fleet of robots sharing one brain, or replaying thousands of logged commands to test a new model (as in the Lesson 19 bake-off). It is the Lesson 16 lesson again: measure first, per decision and per batch.

5. Why it matters for robotics

  • A real robot-like product uses it. comma.ai's openpilot is a driver-assistance system that runs on a small device in the car. Its repo lists tinygrad as a git submodule (.gitmodules), the model daemon openpilot/selfdrive/modeld/modeld.py imports tinygrad, and the driving models ship as *_tinygrad.pkl files. (Checked in the openpilot repo on 7 Nov 2026.)
  • Edge chips are varied. Robots use phone chips, Jetsons and odd accelerators. A framework where a new backend needs only a small set of ops is attractive when you can't get a big vendor library for your chip. The README lists a QCOM (Qualcomm) backend next to the big GPU ones.
  • Latency is control. A control loop has a deadline each cycle. Fewer kernel launches and less memory traffic mean a shorter, steadier step time. Replaying a captured JIT makes each step take about the same time.
  • Don't overclaim. Most robotics research still trains in PyTorch or JAX. tinygrad is a credible way to run a model on unusual hardware, and a great way to learn how frameworks work.

6. Reality check

  • Not 1.0. The README says so. APIs move fast. Our run needed HCQ_RUNTIME_DEV=CPU:CLANG on a Mac without LLVM, on that day's master. Tutorials from a year ago may use names that no longer exist (for example, setting Device.DEFAULT is now deprecated in favour of DEV=…).
  • Install from source. The README recommends pip install -e . from a clone, not a PyPI release.
  • The first call is slow. Every new kernel shape is compiled once. Small jobs look slow (our XOR: 5.2 s). Measure the second run, or use TinyJit.
  • "Tiny" is relative. 9,318 core lines is far bigger than micrograd. It is still small enough to read, unlike PyTorch.
  • Lazy bugs show up late. An error in your maths may only appear at .realize() or .item(), far from the line that caused it.
  • Contributing: the README warns that PRs that look AI-written "will be closed without feedback". Read the contributing rules before sending one.

7. Self-check

What does "lazy" mean in tinygrad, and what makes the work actually happen?

Operations only build a graph of UOps. The work happens when you call .realize(), or read a value with .item(), .tolist() or .numpy().

Why did the README matmul become 1 kernel instead of 2?

The multiply and the sum were in the same graph, and nothing needed the N×N×N products stored. So tinygrad wrote one kernel that multiplies and adds in a loop. Forcing .realize() on the product made it 2 kernels and a 67 MB temporary (at N = 256).

What is a backend, and roughly how much must one support?

The code that talks to one kind of chip: it renders kernels to that chip's language and runs them. The README says about 25 low-level ops.

Why did 4 XOR examples take 5.2 seconds on a GPU?

Most of the time is compiling each new kernel and launching tiny GPU jobs. The maths itself is trivial. GPUs pay off on big batches.

Where does tinygrad sit between your Lesson 15 language model and PyTorch?

Lesson 15 does backprop by hand in plain Python. micrograd automates backprop for single numbers. tinygrad automates it for tensors and compiles fused kernels. PyTorch does the same at full scale with large hand-tuned kernel libraries.
