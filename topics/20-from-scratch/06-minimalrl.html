Start here (no maths needed)

A program can learn to balance a stick on a moving cart just by trying, falling, and keeping score. Nobody tells it the rules of balancing.

Think of it like this

Balance a broom upright on your palm. When it tips left, you move your hand left. Nobody gave you an equation. You dropped it a lot, and slowly your hand learned what works. CartPole is that game for a computer. A pole stands on a cart. Each moment the program pushes the cart left or right. It gets 1 point for every moment the pole stays up, up to 500. Reinforcement learning (RL) is the "drop it a lot and learn" part.

How it works

  1. The program looks at four numbers: where the cart is, how fast it moves, the pole's angle, and how fast the pole is tipping.
  2. It picks "push left" or "push right".
  3. The game says how many points that was worth, and whether the pole fell.
  4. After many tries, it nudges its neural network so good choices become more likely.
  5. Different algorithms (REINFORCE, DQN, PPO…) are different ways of doing step 4.

Why robots care

A pole on a cart is a tiny version of a robot keeping its balance: a two-wheeled robot, a walking robot, an arm holding a full cup. The same algorithms, especially PPO, are used to teach simulated robots to walk.

Try it

  • Balance a ruler on one finger. Then try with your eyes closed for one second. Feeling how fast you lose it shows why the program needs to see the pole's speed, not just its angle.
  • Look at the real training scores in Run it, tested. Notice they go up and down. Learning is wobbly.

Words to know

Episode
One try, from start until the pole falls or time runs out.
Reward
Points the game gives after each move.
Policy
The program's rule for choosing a move.
Q-value
"How many points do I expect if I do this move now and play well after?"
Replay memory
A big notebook of past moves the program re-reads to learn from them again.
Environment
The game or world the program acts in. Here, CartPole.

Going deeper: everything below is the full version. On a first read, look at the real scores and the Robo-Helper experiment, then come back for the code.

1. Summary

TL;DR

minimalRL puts each classic deep RL algorithm in one short PyTorch file, with the environment fixed so you can focus on the algorithm. We ran REINFORCE, DQN and PPO on CartPole-v1 for 3 minutes each. All three learned: REINFORCE peaked at an average of 317, DQN and PPO both hit the maximum of 500. PPO got there fastest in episodes (a perfect 20-episode average at episode 320), then partly collapsed to about 150. Then we wrapped Robo-Helper's room as an environment and trained a DQN to drive to a block. It matched A* exactly, but it broke when the cat moved, unless the cat was part of what it could see.

  • One file each: REINFORCE, Actor-Critic, DQN, PPO, DDPG, A3C, ACER, A2C, SAC, PPO-Continuous, V-trace, plus a PPO-LSTM file not listed in the README.
  • Install snag: "gym > 0.26.2" doesn't exist. 0.26.2 was the last Gym. It installs on Python 3.14 but crashes with numpy 2. We used Gymnasium, Gym's maintained successor, by changing one import.
  • Real results: every run used the full 180-second cap, because each script loops for 10,000 episodes. All three scored 200+ within the cap.
  • Robo-Helper: a DQN learned the 9-step route around the cat in about 200 episodes, and was optimal from all 40 start squares. A* needs no training and plans in microseconds.
  • Where each wins: learned control coped with wheel slip as well as A* replanning every step, and far better than a plan followed blindly. Planning won when the world changed (the cat moved).

2. How the code works: the algorithm ladder

Every file has the same shape: a small network class, a train_net (or train) function, and a main() loop that plays episodes and prints the average score every 20 episodes. The algorithms differ only in what the network predicts and what loss it learns from.

RungFileWhat it learnsThe new idea
1REINFORCE.pyA policy (probabilities of left/right)After an episode, make each action more likely in proportion to the total reward that followed it.
2actor_critic.pyPolicy + a value estimateA "critic" guesses how good a state is, so the actor learns from "better or worse than expected", every few steps instead of every episode.
3a3c.py, a2c.pySame, with many workersSeveral copies of the game play at once (asynchronously in A3C, in lockstep in A2C) for steadier learning.
4ppo.pyPolicy + valueReuse each batch for several updates, but clip how far the policy may move per update. Uses GAE to estimate advantages.
sidedqn.pyQ-values onlyQ-learning with a neural net, a replay memory and a frozen target network.
sideacer.py, vtrace.pyPolicy + value, from older dataCorrections that let the learner use data from a slightly older policy.
continuousddpg.py, sac.py, ppo-continuous.pyActions as real numbersFor torques and speeds, not left/right. These three use Pendulum-v1, not CartPole.

REINFORCE in three lines

# REINFORCE.py (MIT, seungeunrho)
for r, prob in self.data[::-1]:
    R = r + gamma * R
    loss = -torch.log(prob) * R

Walk the episode backwards, adding up discounted reward R. Then push up the log-probability of each action, scaled by R. Good episodes make their actions more likely. That's the whole algorithm.

DQN: the one idea that makes it click

# dqn.py (MIT, seungeunrho)
q_a = q_out.gather(1,a)
max_q_prime = q_target(s_prime).max(1)[0].unsqueeze(1)
target = r + gamma * max_q_prime * done_mask

This is exactly the Q-learning target from Lesson 7: reward plus γ times the best Q at the next state, and just the reward if the episode ended (done_mask = 0). Three things are new:

  • A neural network instead of a table. CartPole's four numbers are continuous, so you can't list every state as a dictionary key. The network fills in Q for states it has never seen.
  • Replay memory (ReplayBuffer, up to 50,000 moves). It trains on random old moves, not only the latest ones, so the examples aren't all near-copies of each other.
  • A target network (q_target), copied from q only every 20 episodes. The target stays still for a while, so the network isn't chasing its own moving guess.

PPO's clip

# ppo.py (MIT, seungeunrho)
surr1 = ratio * advantage
surr2 = torch.clamp(ratio, 1-eps_clip, 1+eps_clip) * advantage
loss = -torch.min(surr1, surr2) + F.smooth_l1_loss(self.v(s) , td_target.detach())

ratio is "how much more likely is this action now than when we collected the data". Clamping it to 0.9–1.1 (eps_clip = 0.1) stops one update from changing the policy too much. That is what lets PPO safely reuse each batch 3 times (K_epoch = 3).

3. Run it, tested (CartPole)

All runs on 7 Nov 2026, MacBook (Apple M4), CPU, Python 3.14.5, torch 2.15.0, in a private venv in a scratch folder. Other jobs were running on the laptop at the same time, so on a quiet machine more episodes would fit in 3 minutes.

The second change is a bug fix. Since Gym 0.26, hitting the 500-step time limit sets truncated, not done. The original loops only stop on done. Once the pole is balanced well, they would keep calling step() past the limit. The comment in REINFORCE.py, "CartPole-v1 forced to terminates at 500 step", is from before that API change. We found this by reading the code. We didn't run the unfixed version.

4. Connect to Robo-Helper: DQN vs A* in our room

Lesson 7 did tabular Q-learning in a maze. dqn.py is the next rung: the same target rule, plus a neural network, replay memory and a target network. So we tested it on Robo-Helper's real room, against the A* planner from Lesson 6.

The setup

  • Room: world.ROOM (10×8, 42 free squares). Start ROBOT_START = (1, 1). Goal: the blue block at (6, 3). The cat sits at sim.CAT = (4, 1), right on the shortest route.
  • Environment (RoomEnv in grid_dqn.py, gym-like reset/step): state = the robot's square as a one-hot list of 80 numbers (plus the cat's square in one version). Actions = N, S, E, W using Lesson 1's move. Reward: −1 per step, −5 for bumping a wall, −10 for bumping the cat (you stay put), +20 for reaching the block. Maximum 60 steps.
  • DQN: the same network shape, replay size (50,000), batch (32), γ (0.98), learning rate, smooth L1 loss and target copy every 20 episodes as dqn.py. Two changes, both honest: exploration starts at 100% and falls to 5% (dqn.py uses 8%→1%, too little to find a block in a room), and each training episode starts on a random free square ("exploring starts").
  • Baselines: lesson06_paths.astar_path told where the cat is, and Lesson 11's real RoboHelper.drive_to, which only discovers the cat when its sensor sees it, then replans.

What it shows:

  • In a room you have a map of, planning wins. A* gives the same 9-step route with zero training, in microseconds. DQN needed hundreds of episodes to learn what A* computes instantly. That's the same honest note as Lesson 7.
  • A learned policy reacts. With 20% wheel slip, a plan followed blindly reached the block only 22% of the time. The DQN reached it 100% of the time, because it picks a move from wherever it actually is. A* matched it only when we made it replan every step. A policy is a closed-loop controller for free.
  • A learned policy only knows what it was shown. When the cat moved onto its route, the position-only DQN drove into the cat 53 times. It cannot see the cat, so it has no reason to change. A* just replanned. When the cat was put into the state and the cat moved around during training, the DQN handled all 40 cat positions with the shortest path. That took 2.7× more episodes and a 160-number input. In a bigger world, "train on every situation" stops being possible. That's where planning, or a learned model plus planning, comes back.

And PPO? In Lesson 12, RLHF by hand, Robo-Helper learned a reward model from a person's route choices, then used best-of-n to pick a route. The lesson explains that real RLHF goes one step further: it trains the policy itself with PPO (or GRPO) on the learned reward, with a KL penalty as a leash. ppo.py is that update in 118 lines. The clip in the loss above is a second leash of the same kind: "improve, but don't move too far from the policy that collected the data".

5. Why it matters for robotics

  • CartPole is balance control. It is the classic inverted pendulum: keep an unstable thing upright by moving its base. Segway-style robots, legged robots and a waiter-robot carrying a tray all face versions of it. Control engineers solve the plain version with a hand-designed controller (for example, LQR), without learning. RL is worth it when the dynamics are too messy to write down.
  • PPO and SAC are workhorses for simulated locomotion. Teaching a simulated legged robot to walk is commonly done with PPO (on-policy, easy to run on many parallel simulators) or SAC (off-policy, more sample-efficient). minimalRL's ppo-continuous.py and sac.py are the continuous-action versions those use, shown here on Pendulum-v1.
  • Sim first, then real. Training needs thousands of falls. Robots learn in simulation, then transfer the policy to hardware. Our room test is a small example of the main risk: a policy can fail badly on something it never saw in training.
  • Don't overclaim. These files are for learning. Real robot RL adds many parallel environments, observation normalisation, domain randomisation and careful reward design.

6. Reality check

  • Gym is dead; use Gymnasium. The README's "gym > 0.26.2" can't be installed. Swap the import, and handle truncated as well as terminated.
  • "Every algorithm can be trained within 30 seconds." We didn't timestamp each line, so we can't say exactly when each passed a given score. All three runs used their full 3-minute cap, because each script loops for 10,000 episodes and never stops on its own.
  • Not every file is CartPole. The README says environments are fixed to CartPole-v1, but ddpg.py, sac.py and ppo-continuous.py use Pendulum-v1.
  • No seeds, so results vary. The files don't set random seeds. Your numbers will differ from ours.
  • Learning can collapse. Our PPO hit 500 then fell to about 150. Save the best checkpoint.
  • For real projects: use a maintained library such as Stable-Baselines3 or CleanRL (single-file implementations with logging). minimalRL is for reading.

7. Self-check

What three things does DQN add to the Lesson 7 Q-learning table?

A neural network that estimates Q for any state, a replay memory of past moves to sample training batches from, and a target network that is only copied every so often, so the target doesn't move with every update.

Why did DQN's score stay around 10 for the first 200 episodes?

It doesn't train until the replay memory holds more than 2,000 moves. Before that, it is acting with random starting weights.

What does PPO's clip do, and why does it help?

It limits how much more or less likely an action can become in one update (here between 0.9× and 1.1×). That makes it safe to reuse the same batch for several updates.

In our room, why did the position-only DQN fail when the cat moved?

The cat wasn't part of its state, so it couldn't know anything changed. It kept choosing the move it learned, into the cat. A* replans with the new obstacle. Adding the cat to the state and training with the cat in many places fixed it.

With 20% wheel slip, why did "A* open-loop" fail but the DQN succeed?

Open-loop A* follows a fixed list of moves, so one slip puts it off its path for good. The DQN chooses from wherever it actually is. A* that replans every step does just as well.
